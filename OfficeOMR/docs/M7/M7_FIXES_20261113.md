## 五、部署时遇到的两个问题（已解决）

### 问题 1：`Error: An unexpected error has occurred.`（在 analyzing source code 阶段）

**原因**：`functions/venv/` 是旧会话留下的**空壳虚拟环境**（只有 pip，没有依赖）。
Firebase CLI 会去找 `<sourceDir>/venv` 并在里面执行
`python -c "import firebase_functions"`，找不到模块就抛错：

```
Running command with virtualenv: command="...\functions\venv\Scripts\activate.bat"
stderr: ModuleNotFoundError: No module named 'firebase_functions'
Error: spawn "...\functions\venv\Scripts\activate.bat" ENOENT
```

**注意：Firebase CLI 不会自动建立 venv**（源码 `lib/deploy/functions/runtimes/python/index.js`
第 96-98 行），它要求你先手动准备好：

```powershell
cd D:\chhsban\OfficeOMR\functions
python -m venv venv
.\venv\Scripts\python.exe -m pip install -r requirements.txt
```

**同时** `requirements.txt` 的 `numpy==1.24.3` 在 Python 3.13 上没有 wheel，
会退回源码编译并失败（`ModuleNotFoundError: No module named 'distutils'`）。
已改为与 `core/pyproject.toml` 一致的版本范围（`numpy>=2.1,<3`、`opencv-python-headless>=4.11,<5`）。

### 问题 2：Cloud Build 失败 —— `SyntaxError` in `./venv/Lib/site-packages/numpy/...`

**原因**：Firebase CLI **不使用 `.gcloudignore`、也不使用 `.gitignore`** 来决定上传内容。
源码 `lib/deploy/functions/prepareFunctionsUpload.js` 第 56 行：

```js
const ignore = config.ignore || ["node_modules", ".git"];
```

`config.ignore` 就是 `firebase.json` 里的 `functions.ignore`。
所以本机 `functions/venv/`（内含 Python 3.13 的 numpy 2.5，用了 PEP 695 `type X = ...` 语法）
被原样打包上传（114.55 MB），Python 3.11 的构建步骤编译它时炸掉。

**修复**：在 `firebase.json` 加入 `functions.ignore`：

```json
"functions": {
  "source": "functions",
  "runtime": "python311",
  "ignore": [
    "venv", "node_modules", ".git", "__pycache__",
    "*.pyc", "*.pyo", ".pytest_cache", "backup",
    "firebase-debug.log", "*-key.json", "serviceAccount*.json"
  ]
}
```

修复后打包体积由 **114.55 MB → 893 KB**。

> `.gcloudignore` 仍然有用，但只对 `gcloud functions deploy`（即 `scripts/deploy.ps1`
> 部署 `recognize_sheet`）生效，对 `firebase deploy` 无效。

### 问题 3：`could not set up cleanup policy`（非致命）

部署成功但提示 Artifact Registry 缺少清理策略（PLAN §9.3 要求）。

```powershell
firebase functions:artifacts:setpolicy --location us-central1 --days 1 -f
```

## 六、2026-11-13 第二轮：`claimAccess` CORS 持续失败的根因

### 现象
即使 13 个函数全部部署成功，浏览器调用 `claimAccess` 仍报：
```
Access to fetch at '.../claimAccess' from origin 'https://omr.mybazaar.my'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header...
POST .../claimAccess net::ERR_FAILED
claimAccess failed: FirebaseError: internal
```
直接打接口得到的是 **Google Frontend 的 HTML 403**：
```html
<h1>Error: Forbidden</h1>
<h2>Your client does not have permission to get URL /claimAccess from this server.</h2>
```

### 根因：firebase-tools 的 bug（更新路径不处理 callable 的 invoker）
`lib/deploy/functions/release/fabricator.js`：

| 路径 | 行号 | 行为 |
|---|---|---|
| `createV2Function` | 322-328 | `else if (isCallableTriggered) → run.setInvokerCreate(..., ["public"])` ✅ |
| **`updateV2Function`** | **421-441** | `isHttpsTriggered` / taskQueue / blocking / schedule 之外**没有 else** → `invoker` 永远是 `undefined` → **`if (invoker)` 为假 → 完全不设置 IAM** ❌ |

而 Python SDK 的 `on_call` 只输出 `callableTrigger`，不输出 `httpsTrigger.invoker`
（`firebase_functions/options.py` `HttpsOptions._endpoint`，第 1127-1151 行）。
所以 discovery 结果（实测）里 13 个函数都是：
```yaml
callableTrigger: {}
```
→ 更新部署时 IAM 被跳过 → 对应的 Cloud Run 服务保持私有 → 403 + CORS 失败。

### 修复
用 Cloud Run v1 IAM API 把每个服务加上 `allUsers` → `roles/run.invoker`。
脚本：**`scripts/grant_public_invoker.ps1`**（复用 Firebase CLI 凭证）。

执行结果：
```

OK  updateglobalsettings / revoketeacher / uploadanswerkeymanually / setuseractive
OK  upsertorg / recognizeandgradesheet / createexam / batchrecognizesheets
OK  uploadanswerkeybyimage / getanswerkey / cleanupjobstudentdata / claimaccess
OK  approveteacher
SKIP recognize-sheet (已由 gcloud --allow-unauthenticated 部署，本来就是公开)
```

验证：
```

createExam   OPTIONS -> HTTP 200  Access-Control-Allow-Origin: *
（其余同样）
```

### 注意事项
- 函数一旦是公开的，后续 `firebase deploy`（走 update 路径）**不会**把它改回私有
  （update 路径根本不碰 IAM），所以修一次即可。
- 若日后**删除并重建**函数，`createV2Function` 会自动设成公开，无需再跑脚本。
- 若脚本报 token 过期，先执行 `firebase login` 再重跑。

## 十、2026-11-13 第三轮：`claimAccess` 把 super_admin 误判为「未授权」

### 现象
CORS 修好后，登录仍然失败，但错误变了：
```
✅ claimAccess result: {error: 'NOT_APPROVED',
                       message: 'User not approved. Please contact administrator.',
                       status: 403, success: false}
🔄 Auth state changed: {isAuthenticated: false, ...}
📋 Showing login page
✅ Logged out
❌ Error loading usage for pwuZBGfUhL0GH2pm10IC: Missing or insufficient permissions.
```

### 原因（连锁反应）
1. `claimAccess` 无条件要求 `allowedUsers/{email}` 文档存在。
   但 **super_admin 是用 `tools/bootstrap_admin.py` 只设 custom claims，
   没有 `allowedUsers` 文档**（PLAN §3.2 就是这么设计的）→ 管理员被判 `NOT_APPROVED`。
2. `login.js` 看到 `accessResult.error` 就**3 秒后自动登出** —— 即使该账号其实已经有
   有效的 super_admin claims。
3. 登出后，`admin.js render() → loadUsage()` 正在进行的 Firestore 读取失去 `request.auth`
   → `isSuperAdmin()` 为 false → 「Missing or insufficient permissions」。
   （**所以那个 usage 权限错误只是被登出后的副作用，rules 本身是正确的。**）

### 修复
| 文件 | 改动 |
|---|---|
| `functions/callables_m6.py` | `claimAccess` 在查 `allowedUsers` 之前，先判断 token 是否已是 `role == 'super_admin'`，是则直接回传成功（不再要求 allowedUsers 文档） |
| `web/js/pages/login.js` | `accessResult.error` 为真时，先确认 `getCurrentUserClaims()` 是否已有 `role`；有则**不登出**，交给 `app.js` 依 claims 路由 |
| `web/js/pages/admin.js` | `loadUsage()` 开头加 `if (!this.authFlow.auth.currentUser) return;`，避免登出后仍去读 Firestore |

### 验证
```

admin.js  has logout guard               : True
```

## 十一、2026-11-13 第四轮：教师登入后停在登录页（路由时序 bug）

### 现象
`admin.html`（super_admin）已完全正常：
```
📊 Showing admin page
✅ claimAccess result: {data: {...}, status: 200, success: true}
```
但一般教师登入后仍停在登录页：
```
✅ Google sign-in successful: ...
🔄 Auth state changed: ▶ Object
⚠️ Unknown role: undefined      ← 此刻 claims 还没设置（claimAccess 尚未完成）
📋 Showing login page
✅ claimAccess result: ▶ Object  ← claimAccess 这时才设置好 claims
📋 Showing login page            ← 没有任何东西触发重新路由，卡住了
```

### 原因
登录流程是「先 signInWithPopup → Firebase 触发 onAuthStateChanged → 此时还没有
custom claims → 判定为 unknown role → 显示登录页」；随后 `login.js` 才调用
`claimAccess` 去设置 claims。**Firebase 不会因为 claims 变更而再次触发
`onAuthStateChanged`**，而旧代码里那句注解「等待路由改变」其实没有任何东西会去改变路由。

### 修复
| 文件 | 改动 |
|---|---|
| `web/js/app.js` | 新增 `refreshRouting()`：读取最新 claims 并重新调用 `onAuthStateChanged()` 路由 |
| `web/js/pages/login.js` | `claimAccess` 成功后，先 `await user.getIdToken(true)` 强制刷新 token，再调用 `window.app.refreshRouting()`；「已有 claims」分支同样调用 |

### 验证
```
login.js has refreshRouting : True
app.js   has refreshRouting : True
```

### 使用方式
1. 在 `admin.html` →「👨‍🏫 教师管理」→ 新增教师，填入对方的 Google 邮箱 + 所属组织。
2. 对方用该 Google 账号登入 `omr.mybazaar.my` → claimAccess 会设置
   `{role: 'teacher', orgId: ...}` 并绑定 uid → `refreshRouting()` 后进入教师页面。

## 十二、2026-11-13 第五轮：`Failed to set user claims`（INSUFFICIENT_PERMISSION）

### 现象
`astcws@gmail.com` 确认已存在于 `allowedUsers/astcws@gmail.com`
（`active: true, role: "teacher", orgId: "chhs"`），但登录仍失败：
```
claimAccess result: {error: 'INTERNAL_ERROR', message: 'Failed to set user claims',
                     status: 500, success: false}
```

### 定位过程
`firebase functions:log` 只吐出审计日志，看不到错误；
改用 **Cloud Logging API**（`logging.googleapis.com/v2/entries:list`）抓 `claimaccess` 服务日志，
终于看到关键一行：
```
Failed to set custom claims: The credential used to initialize the SDK has
insufficient permissions to perform the requested operation.
See https://firebase.google.com/docs/admin/setup ...
(INSUFFICIENT_PERMISSION)
```

### 根因
gen2 函数以 **Compute Engine 默认服务账号** 执行
（审计日志 `serviceConfig.serviceAccountEmail` = `601814582794-compute@developer.gserviceaccount.com`）。
该 SA 在项目 IAM 里只有 artifactregistry.writer / cloudbuild.builds.builder /
datastore.user / logging.logWriter / storage.object* 等角色，
**没有 `roles/firebaseauth.admin`** —— 所以 `auth.set_custom_user_claims()` 被拒。

（`roles/firebaseauth.admin` 当时只绑在 `firebase-adminsdk-fbsvc@...` 上，
那是给本机 Admin SDK 用的，跟 Cloud Functions 的运行时 SA 无关。）

> 这也解释了为什么先前的 super_admin 测试「看起来成功」：
> 我在第三轮加的 super_admin 快速通道在调用 `set_custom_user_claims` **之前**就返回了，
> 所以从未真正测到这行。

### 修复
给运行时 SA 补上 `roles/firebaseauth.admin`（专案 IAM policy）：

```
--- BEFORE ---
```
