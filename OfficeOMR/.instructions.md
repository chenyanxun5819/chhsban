# OfficeOMR 项目工作指南

## 📁 整体目录组织原则

**重要：所有文件必须按用途分类放置，不要到处乱放！**

### 项目根目录结构

```
OfficeOMR/
├── README.md                    ← 项目主文档（保留在根目录）
├── docs/                        ← 【所有工作文档都在这里】
│   ├── M1/                      ← M1 阶段文档
│   ├── M2/                      ← M2 阶段文档
│   ├── M3/                      ← M3 阶段文档
│   ├── M4/                      ← M4 阶段文档
│   ├── M5/                      ← M5 阶段文档
│   ├── M6/                      ← M6 阶段文档
│   └── [通用文档]               ← 不属于特定阶段的文档
│
├── scripts/                     ← 【生产环境脚本（系统运行必需）】
│   ├── deploy.ps1              ← 部署脚本
│   ├── setup.ps1               ← 设置脚本
│   ├── init-firestore.ps1      ← 初始化脚本
│   └── ...
│
├── temp/                        ← 【临时开发脚本（建立过程中产生）】
│   ├── debug/                   ← 调试脚本
│   ├── test/                    ← 测试脚本
│   └── archive/                 ← 已完成阶段的归档
│
├── src/、functions/、web/       ← 项目代码文件夹
└── [其他项目文件夹]
```

## 📁 文档组织原则

### 文档分类规则

**按阶段分类（优先）**
- 如果文档带有阶段标识（M1、M2、M3...M6），则放入相应的阶段文件夹
- 例如：`M5_EXECUTION_PLAN.md` → `docs/M5/`
- 包括：进度报告、阶段总结、阶段计划、检查清单等

**通用文档（docs 根目录）**
- 不属于特定阶段的文档放在 `docs/` 根目录
- 例如：
  - `DECISIONS.md` - 项目决策记录
  - `PLAN.md` - 整体项目计划
  - `SCAN_GUIDE.md` - 使用指南
  - `STATUS.md` - 当前状态概览
  - `FUTURE.md` - 未来规划
  - 配置类：`FIREBASE_LOGIN_MANUAL.md`、`GITHUB_AUTO_DEPLOY.md` 等

**排除的文件**
- 代码文件（.py、.js、.ts 等）
- 配置文件（firestore.rules、firebase.json 等）
- 项目根目录保持 `README.md` 作为入口

## 📝 新建文档流程

1. **确认文档性质**
   - 是否属于特定阶段？→ 放入 `docs/{MX}/`
   - 是否是通用文档？→ 放入 `docs/`

2. **命名规范**
   - 阶段文档：`{MX}_[描述].md` 或 `[描述]_{MX}.md`
   - 通用文档：`[描述].md`
   - 使用大写和下划线分隔单词

3. **放置位置**
   - 永远不要在项目根目录创建工作报告文档
   - 永远不要在 `src/`、`functions/` 等代码目录放文档
   - 所有工作文档都属于 `docs/` 目录

## 🔗 常见文档类型

- **阶段计划**：`docs/{MX}/MX_EXECUTION_PLAN.md`
- **进度报告**：`docs/{MX}/MX_PROGRESS.md`、`docs/{MX}/MX_SESSION_REPORT.md`
- **阶段总结**：`docs/{MX}/MX_SESSION_FINAL_REPORT.md`、`docs/{MX}/MX_PROJECT_SUMMARY.md`
- **检查清单**：`docs/{MX}/MX_CHECKLIST.md`、`docs/{MX}/MX_STAGE_A_CHECKLIST.md`
- **部署指南**：`docs/{MX}/M6_QUICK_START.md`、`docs/{MX}/DEPLOY_GUIDE.md`

## ✅ 文档维护

- 定期检查 `docs/` 目录结构是否正确
- 已完成的阶段文档保留在相应的阶段文件夹
- 进行中的工作文档可以放在相应阶段文件夹中
- 跨阶段的决策或规划放在 `docs/` 根目录

## 🔧 脚本组织原则

**重要：脚本必须按用途分类，区分生产和临时代码！**

### 脚本分类规则

**scripts/ 目录 - 生产环境脚本**
- 放置系统运行和部署时必需的脚本
- 这些脚本由 CI/CD 或手动部署时使用
- 包括：deploy.ps1、setup.ps1、init-firestore.ps1 等
- 例子：`DEPLOY_M6_STAGE_A.ps1` 应该在 `scripts/` 中

**temp/ 目录 - 临时开发脚本**
- 放置开发过程中产生的临时脚本
- 这些脚本不是生产代码的一部分
- 进一步分类到子目录：
  - `temp/debug/` - 调试脚本（debug_*.py、inspect_*.py 等）
  - `temp/test/` - 测试脚本（test_*.py、step*.py 等）
  - `temp/archive/` - 已完成阶段的归档脚本

**排除的文件**
- 代码逻辑文件（src/、functions/、core/ 等）放在各自的文件夹
- 配置文件（firestore.rules、firebase.json 等）不属于任何脚本目录

### 脚本命名规范

- **部署脚本**：`DEPLOY_[描述].ps1` 或 `setup-[描述].ps1`
- **调试脚本**：`debug_[名称].py` 或 `debug-[名称].ps1`
- **测试脚本**：`test_[名称].py` 或 `step[N]_[描述].py`
- 使用大写和下划线分隔单词

### 脚本完成后的处理

1. **当阶段完成时**
   - 更新相应的 M{X} 文档到 `docs/{MX}/`
   - 将该阶段的临时脚本移到 `temp/archive/M{X}/`
   - 如果脚本成为生产代码，移到 `scripts/`

2. **文件保留策略**
   - 正在进行的阶段：脚本留在 `temp/` 中便于快速访问
   - 完成的阶段：脚本归档到 `temp/archive/{MX}/` 保存历史
   - 后续参考：从 `temp/archive/` 查询历史脚本

## 📋 Log 和 Output 文件组织规范

**重要：Log 文件必须按用途分类，不要在根目录或其他地方乱放！**

### Log/Output 分类规则

**temp/debug/ - 调试输出日志**
- 调试脚本（debug_*.py、inspect_*.py）的输出
- 文件名示例：debug_output.log、debug_*.log
- 保留时间：本阶段内，用完可删除

**temp/test/ - 测试输出日志**
- 测试脚本（test_*.py、step*.py）的输出
- 验证脚本和部署测试的输出
- 文件名示例：test_output.txt、step1_output.log、verify_output.log、deploy-debug.log
- 保留时间：本阶段内，用完可删除

**docs/{MX}/ - 生产部署日志（长期保存）**
- 重要的生产部署日志和记录
- 文件名示例：M6_DEPLOYMENT_2026-11-11.log、M6_STAGE_A_DEPLOY_SUCCESS.log
- 保留时间：长期保存以供审计和回顾

### Log/Output 命名规范

- **调试日志**：`debug_[名称].log` 或 `debug_output.log`
- **测试日志**：`test_[名称].log`、`test_[名称].txt` 或 `test_output.txt`
- **步骤输出**：`step[N]_output.log`
- **验证输出**：`verify_[名称].log` 或 `verify_output.log`
- **部署日志**：`deploy-[描述].log` 或 `deploy_output.txt`
- **生产日志**：`{MX}_DEPLOYMENT_[DATE].log`

### Log 文件输出方式

```powershell
# 调试脚本输出
python debug_omr.py > temp/debug/debug_output.log

# 测试脚本输出
python test_omr.py > temp/test/test_output.txt

# 步骤验证输出
python step1_reproduce_200dpi_issue.py > temp/test/step1_output.log

# 部署日志（重要记录保存到 docs）
firebase deploy --debug 2>&1 | Tee-Object -FilePath "docs/M6/M6_DEPLOYMENT_$(Get-Date -Format 'yyyy-MM-dd').log"
```

### 排除的文件

- 代码文件（.py、.js、.ts 等）不属于 log/output 目录
- 配置文件（firestore.rules、firebase.json 等）不属于 log/output 目录

## 📋 完整工作流程

### 新建文档时

```
确认文档类型
    ↓
【属于特定阶段】→ 放在 docs/{MX}/
    ↓
【不属于特定阶段】→ 放在 docs/
```

### 新建脚本时

```
确认脚本用途
    ↓
【生产部署脚本】→ 放在 scripts/
    ↓
【临时开发脚本】→ 放在 temp/ 相应子目录
    ├─ 调试 → temp/debug/
    ├─ 测试 → temp/test/
    └─ 不确定 → temp/archive/
```

### 阶段完成时

```
清理工作
    ↓
1. 将工作文档整理到 docs/{MX}/
2. 将临时脚本移到 temp/archive/{MX}/
3. 确认生产脚本已在 scripts/
4. 更新进度文档
```

## 🎯 原则总结（记住这些！）

| 项目 | 应该放在 | 不应该放在 |
|------|--------|---------|
| 工作报告、进度、计划 | `docs/{MX}/` 或 `docs/` | 根目录、其他位置 |
| 部署/设置脚本 | `scripts/` | 根目录、其他位置 |
| 调试/测试脚本 | `temp/debug/` 或 `temp/test/` | 根目录、其他位置 |
| 代码逻辑文件 | `src/`、`functions/` 等 | `docs/`、`temp/` |
| 配置文件 | 项目根目录 | `docs/`、`scripts/` |

## 📝 为什么要这样做

✅ **代码整洁**
- 生产和临时代码清晰分离
- 避免混淆哪些脚本是"真正需要"的

✅ **易于维护**
- 新人可以快速理解项目结构
- 文档集中在 docs/，易于查找

✅ **历史记录**
- 完成的阶段脚本保留在 archive 中
- 可以参考以前的实现方式

✅ **CI/CD 友好**
- `scripts/` 中的脚本可以自动化部署
- 不会意外部署测试代码
